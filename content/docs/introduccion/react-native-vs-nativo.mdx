## Introducción conceptual

"Nativo" significa escribir la app con las herramientas oficiales de cada plataforma: **Swift/SwiftUI** con Xcode para iOS y **Kotlin/Jetpack Compose** con Android Studio para Android. React Native también produce interfaces nativas, pero la lógica y la UI se describen una sola vez en React.

La pregunta útil no es "¿cuál es mejor?", sino **"¿qué necesita este producto y este equipo?"**.

| --- | --- | --- |
| Rendimiento de UI típica | Excelente | Excelente (Fabric + Hermes) |

| Velocidad de desarrollo | Dos implementaciones | Una implementación, Fast Refresh |

| Tamaño del equipo | Mayor | Menor |
| Actualizaciones sin tienda | No | Sí, con EAS Update (solo JS y assets) |

## Ejemplo práctico

La misma pantalla mínima, un saludo con un botón, escrita en las tres tecnologías. Observa que la estructura mental (estado + vista declarativa) es casi idéntica: SwiftUI y Compose se inspiraron en el modelo de React.

<CodeTabs>

```tsx title="React Native (TSX)"
import { useState } from 'react';
import { Button, Text, View } from 'react-native';

export default function Greeting() {
  const [count, setCount] = useState(0);
  return (
    <View style={{ flex: 1, alignItems: 'center', justifyContent: 'center', gap: 12 }}>
      <Text style={{ fontSize: 22 }}>Pulsaste {count} veces</Text>
      <Button title="Pulsar" onPress={() => setCount(count + 1)} />
    </View>
  );
}
```

```swift title="iOS (SwiftUI)"
import SwiftUI

struct Greeting: View {
    @State private var count = 0

    var body: some View {
        VStack(spacing: 12) {
            Text("Pulsaste \(count) veces").font(.title2)
            Button("Pulsar") { count += 1 }
        }
    }
}
```

```kotlin title="Android (Compose)"
@Composable
fun Greeting() {
    var count by remember { mutableIntStateOf(0) }
    Column(
        modifier = Modifier.fillMaxSize(),
        horizontalAlignment = Alignment.CenterHorizontally,
        verticalArrangement = Arrangement.spacedBy(12.dp, Alignment.CenterVertically)
    ) {
        Text("Pulsaste $count veces", fontSize = 22.sp)
        Button(onClick = { count++ }) { Text("Pulsar") }
    }
}
```

</CodeTabs>

## Explicación del código

- En los tres casos hay **estado local** (`useState`, `@State`, `remember`) y una **vista declarativa** que se vuelve a calcular cuando cambia.
- Con React Native escribes ese componente **una vez** y se ejecuta en iOS y Android. Con nativo, mantienes las dos versiones sincronizadas a mano.
- Cuando necesites algo que solo existe en una plataforma, React Native permite escribir esa parte en Swift o Kotlin con la [Expo Modules API](https://docs.expo.dev/modules/overview/) y llamarla desde TypeScript. No es "todo o nada".

## Buenas prácticas

- **Evalúa el producto, no la tecnología.** Apps de negocio, formularios, listas, e-commerce, redes sociales o fintech encajan muy bien en React Native.
- **Combina cuando haga falta.** Muchas empresas usan React Native para la mayoría de pantallas y módulos nativos para piezas críticas.
- **Considera el equipo.** Si tu equipo ya domina React y TypeScript, la curva de entrada es mucho menor.

### Errores comunes

- Suponer que React Native "no puede" usar una API nativa: casi siempre existe un módulo de Expo o de la comunidad, y si no, puedes crearlo.
- Elegir React Native y luego escribir la mitad de la app en nativo por desconocimiento: primero aprende los patrones de rendimiento de [Calidad y buenas prácticas](/docs/calidad/rendimiento).

### Cuándo usar otra solución

Elige nativo puro si construyes un juego, una app de edición multimedia en tiempo real, una app que depende sobre todo de funciones de sistema muy recientes (widgets complejos, realidad aumentada avanzada) o si ya tienes dos equipos nativos consolidados y sin intención de unificarlos.
