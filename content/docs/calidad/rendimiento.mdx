## Introducción conceptual

El rendimiento percibido de una app móvil se resume en tres preguntas: **¿arranca rápido?**, **¿responde al instante a los toques?** y **¿se desplaza y anima con fluidez (60–120 fps)?**. Las causas más habituales de problemas son:

- **Renders innecesarios**: un cambio de estado provoca que se vuelvan a renderizar muchos componentes que no cambiaron.
- **Trabajo pesado en el hilo de JavaScript**: cálculos, parseo de JSON enormes o lógica en cada render que retrasan la respuesta a los toques.
- **Imágenes** demasiado grandes y listas mal configuradas.
- **Bundles grandes** que retrasan el arranque.

## Ejemplo práctico

**Problema típico**: un contexto con un valor que cambia constantemente re-renderiza toda la pantalla.

```tsx title="Antes: todo se re-renderiza cada segundo"
function DashboardScreen() {
  const [now, setNow] = useState(Date.now());
  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), 1000);
    return () => clearInterval(id);
  }, []);

  return (
    <ScrollView>
      <Text>{new Date(now).toLocaleTimeString()}</Text>
      <SalesChart />        {/* costoso, se re-renderiza cada segundo */}
      <TopProductsList />   {/* costoso, se re-renderiza cada segundo */}
    </ScrollView>
  );
}
```

```tsx title="Después: el estado vive donde se usa"
function LiveClock() {
  const [now, setNow] = useState(Date.now());
  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), 1000);
    return () => clearInterval(id);
  }, []);
  return <Text>{new Date(now).toLocaleTimeString()}</Text>;
}

function DashboardScreen() {
  return (
    <ScrollView>
      <LiveClock />          {/* solo este componente se re-renderiza */}
      <SalesChart />
      <TopProductsList />
    </ScrollView>
  );
}
```

Herramientas para medir:

```bash
# Abrir React Native DevTools (Profiler, componentes, consola, red)
npx expo start   # y pulsa "j"

# Analizar el tamaño del bundle con Expo Atlas
EXPO_ATLAS=true npx expo export --platform android
npx expo-atlas .expo/atlas.jsonl

# Probar el rendimiento real: build de release en el dispositivo
npx expo run:android --variant release
npx expo run:ios --configuration Release
```

## Explicación del código

- **Bajar el estado** (*state colocation*): mover el estado al componente más pequeño que lo necesita es la optimización más eficaz y no requiere memoización. `LiveClock` se renderiza cada segundo; el resto de la pantalla, no.
- **El Profiler de React Native DevTools** graba una interacción y muestra qué componentes se renderizaron, cuántas veces y cuánto tardaron. Activa "Highlight updates" para ver los renders en pantalla.
- **Expo Atlas** muestra qué módulos ocupan el bundle: librerías enormes importadas para una función, iconos completos, *polyfills* innecesarios.
- **Build de release**: el modo desarrollo incluye comprobaciones extra y es mucho más lento; mide siempre en release.

## Buenas prácticas

- **Mide primero** (Profiler, Perf Monitor del menú de desarrollo) y optimiza lo que los datos señalen.
- **Coloca el estado** lo más abajo posible; divide contextos y usa selectores en stores.
- **Arranque**: evita trabajo síncrono pesado al inicio, carga datos tras el primer render y mantén la splash solo lo imprescindible.
- **Imágenes**: tamaños adecuados, `expo-image` con caché, formatos modernos (WebP/AVIF).
- **Animaciones** en el hilo de UI con Reanimated.
- **Activa React Compiler** para reducir renders sin memoización manual.

### Errores comunes

- Medir en modo desarrollo y concluir que la app es lenta.
- Dejar `console.log` con objetos enormes en bucles o en cada render.
- Importar librerías completas (por ejemplo, todas las utilidades de una librería de fechas) para una sola función.

### Cuándo usar otra solución

Si una tarea es intensiva en CPU (procesar imágenes, cifrado, cálculos grandes), muévela al servidor, a un módulo nativo o a un runtime de worklets en segundo plano. Para listas, consulta [Optimización de FlatList](/docs/calidad/optimizacion-de-flatlist).
